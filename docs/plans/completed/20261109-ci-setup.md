# GitHub Actions: CI, Docker images, releases

The repo is public on GitHub (`netxms/web-ui`) and has no workflows. Add three:

- every commit: lint and release build
- every commit: both Docker images (console, demo), built natively on amd64 and arm64 runners
- a `v*` tag: GitHub release with the bundle, and the images published under the version

## Decisions

- **Triggers.** CI and Docker run on `push` to any branch and on `pull_request` (fork PRs get
  checked too). Same-repo PR branches run twice; accepted over the complexity of filtering.
  `concurrency` cancels a superseded run on the same ref.
- **What gets pushed.** Branch and PR builds only build the images (no registry login, cache
  only). Pushes to `main` publish `:main` and `:sha-<short>`; `v*` tags publish `:<version>`,
  `:<major>.<minor>` and `:latest`; a prerelease tag (`v1.0.0-rc.1`) only `:<version>`. Fork PRs
  never get a token with `packages: write`.
- **Multi-arch.** One build job per (target × platform) on the native runner, pushing by digest;
  a merge job per target assembles the manifest list with `docker buildx imagetools create` and
  the tags from `docker/metadata-action`. Build cache `type=gha`, scoped per target and platform.
- **Release.** A separate `release.yml` on `v*` tags: checks the tag equals
  `v` + `package.json` version (fails otherwise), runs `yarn lint:ci` and `yarn build`, packs
  `dist/` as `netxms-console-<version>.tar.gz` plus a `.sha256`, and creates the release with
  `gh release create --generate-notes`. Images for the tag come from `docker.yml`, not from
  here, so there is one image build path.
- **Unit tests are not in CI**: the request was lint and build. Adding `yarn test:unit --run` is
  one step if wanted later.
- Actions pinned to current major tags at the time of writing (`actions/checkout@v7`,
  `actions/setup-node@v7`, `actions/cache@v6`, `docker/*@vN`), `permissions` minimal per
  workflow/job.
- **One version check, run before anything is published.** A `v*` tag must equal `v` +
  `package.json` version. `release.yml` and `docker.yml` both run it before building, so a
  mismatched tag publishes neither a release nor images.

workflow runs, run locally the same way (`yarn lint:ci`, `yarn build`, `docker build` of the
targets the task touches). The workflows themselves run only once the branch is pushed, which
this run does not do.

`--target demo` pass locally (arm64 host). The tag check exits 0 for `v0.9.0` and 1 for `v1.0.0`
against version `0.9.0`. The manifest step's tag and digest arrays checked in bash 5 with sample
metadata JSON. Registry push, the GHA cache and the arm64 runner run only once the branch is pushed.

➕ `prepare` always runs and outputs `publish`; only its tag-check step is conditional, so branch
and PR builds do not skip. Per-arch images carry the `docker/metadata-action` OCI labels (source,
revision), which link the GHCR packages to the repo. `type=sha` is limited to branch pushes, so a
tag publishes only the version tags and `latest`.
➕ Review: image names come from `prepare`'s lowercased `ghcr.io/<owner>`, since a fork owner can
have uppercase letters and the image exporter rejects them.
⚠️ The build job holds `packages: write` on branch and PR runs too: one job both builds and
pushes, and permissions cannot be conditional. Login and push are gated on `publish`, and fork
PR tokens stay read-only. Both agents accepted this over splitting the job.
➕ revmux: the merge job fails unless exactly one digest per platform is present (a partial
re-run after the 1-day artifact retention would otherwise publish a single-arch manifest), and
checks the published index lists `linux/amd64` and `linux/arm64`, ignoring the `unknown/unknown`
attestation entries.
➕ Docker actions at current majors: `metadata-action@v6`, `setup-buildx-action@v4`,
`login-action@v4`, `build-push-action@v7`; artifacts via `upload-artifact@v7`,
`download-artifact@v8`.
